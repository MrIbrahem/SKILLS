This page documents how mwclient handles transient failures through automatic retries and back-off delays. It covers the `Sleepers` and `Sleeper` classes in `mwclient/sleep.py`, how they are configured on `Site`, where in the request pipeline they are invoked, and when `MaximumRetriesExceeded` is raised.

For a broader explanation of how API calls flow through the stack, see the [API Request Pipeline](/mwclient/mwclient/2.3-api-request-pipeline). For the exception class itself, see [Error Handling](/mwclient/mwclient/6-error-handling).

---

## Overview

mwclient has **two independent retry loops**, each operating at a different level of the call stack:

| Loop | Location | Triggers |
| --- | --- | --- |
| Transport-level | `Site.raw_call` | HTTP 5xx, HTTP 429, DB lag header, `ConnectionError`, `Timeout` |
| Application-level | `Site.api` + `Site.handle_api_result` | `DBConnectionError`, `DBQueryError` API errors, OAuth nonce reuse |

Both loops use the same `Sleeper` mechanism, but each call to `self.sleepers.make()` creates an **independent** sleeper with its own retry counter. A failure in one loop does not consume retry budget in the other.

### Sleepers

`Sleepers` is a factory that holds the shared configuration (`max_retries`, `retry_timeout`, `callback`) and produces `Sleeper` instances on demand via `make()`. A single `Sleepers` instance is created per `Site` object at construction time.

[mwclient/sleep.py L10-L49](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/sleep.py#L10-L49)

### Sleeper

A `Sleeper` tracks retry state for **one specific operation**. Each call to `sleeper.sleep()` does the following:

1. Increments `self.retries`.
2. If `self.retries > self.max_retries`, raises `MaximumRetriesExceeded`.
3. Invokes the user-supplied `callback(sleeper, retries, args)`.
4. Computes `timeout = retry_timeout * (retries - 1)`.
5. If a caller-specified `min_time` exceeds `timeout`, uses `min_time` instead.
6. Calls `time.sleep(timeout)`.

[mwclient/sleep.py L52-L103](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/sleep.py#L52-L103)

### Back-off Formula

The sleep duration grows linearly with the retry count:

```
timeout = retry_timeout × (retries − 1)
```

With the default `retry_timeout=30` and `max_retries=25`:

| Retry # | Sleep (seconds) |
| --- | --- |
| 1 | 0 |
| 2 | 30 |
| 3 | 60 |
| 4 | 90 |
| … | … |
| 25 | 720 |
| 26 | → raises `MaximumRetriesExceeded` |

## Configuration on Site

`Sleepers` is instantiated in `Site.__init__` and stored as `self.sleepers`:

```
self.sleepers = Sleepers(max_retries, retry_timeout, wait_callback)
```

[mwclient/client.py L162](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/client.py#L162-L162)

The relevant constructor parameters are:

| Parameter | Type | Default | Description |
| --- | --- | --- | --- |
| `retry_timeout` | `int` | `30` | Seconds to sleep per completed retry |
| `max_retries` | `int` | `25` | Maximum number of retries before giving up |
| `wait_callback` | `Callable` | no-op lambda | Called on each retry with `(sleeper, retries, args)` |

### Transport-Level Retry (raw_call)

`raw_call` creates its own sleeper at [mwclient/client.py L550](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/client.py#L550-L550)

 and loops unconditionally. The following conditions trigger `sleeper.sleep()`:

* **Database lag header**: The response has an `x-database-lag` header. The wait time is taken from the `retry-after` header value and passed as `min_time` to `sleeper.sleep()`. [mwclient/client.py L577-L583](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/client.py#L577-L583)
* **HTTP 5xx**: Server error responses. [mwclient/client.py L586-L596](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/client.py#L586-L596)
* **HTTP 429**: Too Many Requests. Treated identically to 5xx. [mwclient/client.py L587-L588](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/client.py#L587-L588)
* **`ConnectionError` or `Timeout`**: Network-level failures caught from `requests`. [mwclient/client.py L599-L610](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/client.py#L599-L610)

If `retry_on_error=False` is passed (used by `site_init`), network and 5xx errors are re-raised immediately without sleeping.

When `MaximumRetriesExceeded` is caught inside `raw_call`, the method re-raises the original triggering exception (the `HTTPError` from `stream.raise_for_status()` or the original `ConnectionError`/`Timeout`). [mwclient/client.py L613-L621](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/client.py#L613-L621)

### Application-Level Retry (api / handle_api_result)

`api` creates its own sleeper at [mwclient/client.py L424](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/client.py#L424-L424)

 and runs a `while True` loop. `handle_api_result` returns `False` to signal "retry" in two cases:

| API error code | Cause | Action |
| --- | --- | --- |
| `internal_api_error_DBConnectionError` | MediaWiki DB connectivity issue | `sleeper.sleep()`, return `False` |
| `internal_api_error_DBQueryError` | MediaWiki DB query failure | `sleeper.sleep()`, return `False` |
| `mwoauth-invalid-authorization` (with "Nonce already used") | OAuth nonce collision | `sleeper.sleep()`, return `False` |

All other `error` keys result in an `errors.APIError` being raised immediately.

[mwclient/client.py L471-L495](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/client.py#L471-L495)

## MaximumRetriesExceeded

`MaximumRetriesExceeded` is defined in `mwclient/errors.py` as a subclass of `MwClientError` (which itself extends `RuntimeError`).

[mwclient/errors.py L22-L24](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/errors.py#L22-L24)

It is raised by `Sleeper.sleep()` when `self.retries > self.max_retries`. The exception is instantiated with `(self, self.args)` — the `Sleeper` instance itself and whatever context was passed to `sleepers.make()`.

[mwclient/sleep.py L94-L95](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/sleep.py#L94-L95)

**Where it propagates:**

| Call site | Behavior on `MaximumRetriesExceeded` |
| --- | --- |
| `raw_call` | Caught internally; re-raises original HTTP or network exception |
| `api` | Propagates upward uncaught; caller receives `MaximumRetriesExceeded` |
| `login` | Documented as a possible raise; propagates to caller |

## The wait_callback Hook

The `wait_callback` parameter on `Site.__init__` lets callers observe each retry attempt. The signature is:

```
callback(sleeper: Sleeper, retries: int, args: Any) -> Any
```

* `sleeper`: the `Sleeper` instance (exposes `.max_retries`, `.retry_timeout`, `.retries`)
* `retries`: current retry count (1-indexed)
* `args`: context passed to `sleepers.make()` — for `raw_call` this is the tuple `(script, data)`, for `api` it is `None`

The callback is invoked **before** the sleep, so it can be used to log progress or cancel the retry by raising an exception.

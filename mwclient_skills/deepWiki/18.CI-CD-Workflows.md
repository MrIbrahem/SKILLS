This page documents the three GitHub Actions workflows that automate testing, coverage reporting, and package publishing for mwclient. It covers what triggers each workflow, what each job does, and how they relate to the tox environment matrix.

For the local tox environment setup and how to run tests manually, see [Testing](/mwclient/mwclient/7.1-testing). For the maintainer steps that precede a release (version bumping, tagging), see [Release Process](/mwclient/mwclient/7.3-release-process).

---

## Overview

The CI/CD system consists of three workflow files in `.github/workflows/` and a Dependabot configuration for keeping Actions dependencies current.

| Workflow file | Name | Trigger | Purpose |
| --- | --- | --- | --- |
| `tox.yml` | Test Python package with Tox | `push`, `pull_request` | Run unit tests across Python 3.7–3.15, report coverage |
| `integration.yml` | Run integration tests | `push`, `pull_request` | Run container-based integration tests via Podman |
| `release.yml` | Build and publish to PyPI | `push` (tag filter) | Build sdist+wheel, publish to PyPI, sign with Sigstore, create GitHub Release |

## tox.yml — Unit Test Workflow

### What it does

This workflow runs the tox test suite across a matrix of Python versions on every push and pull request. On Python 3.14 specifically, it also generates and uploads a coverage report to Coveralls.

### Matrix configuration

[.github/workflows/tox.yml L14-L28](https://github.com/mwclient/mwclient/blob/47ea5b29/.github/workflows/tox.yml#L14-L28)

The matrix covers Python 3.7 through 3.15 alpha. Python 3.7 runs on `ubuntu-22.04` (the last Ubuntu release with Python 3.7 support); all other versions run on `ubuntu-latest`.

| Python version | OS |
| --- | --- |
| 3.7 | ubuntu-22.04 |
| 3.8 – 3.13 | ubuntu-latest |
| 3.14 | ubuntu-latest |
| 3.15.0-alpha – 3.15 | ubuntu-latest |

### [gh-actions] mapping in tox.ini

The `tox-gh-actions` package maps the runner's active Python version to specific tox environments. This mapping is defined in [tox.ini L5-L16](https://github.com/mwclient/mwclient/blob/47ea5b29/tox.ini#L5-L16)

:

| Python version | tox environments invoked |
| --- | --- |
| 3.7 | `py37` |
| 3.8 | `py38` |
| 3.9 | `py39` |
| 3.10 | `py310` |
| 3.11 | `py311` |
| 3.12 | `py312` |
| 3.13 | `py313` |
| 3.14 | `py314`, `flake`, `integration`, `mypy` |
| 3.15 | `py315` |

Python 3.14 is the only version that triggers `flake`, `mypy`, and `integration` environments in addition to the standard unit test run.

## integration.yml — Integration Test Workflow

### What it does

This workflow runs the container-based integration test suite using Podman. It always uses Python 3.14 and does not include a version matrix. It runs on every push and pull request.

### Why Podman

The integration tests in `test/integration.py` spin up a real MediaWiki instance inside a container. The runner installs `podman` via `apt-get`, which gives access to a daemonless container runtime that works in the GitHub Actions `ubuntu-latest` environment without elevated privileges.

## release.yml — Build and Publish Workflow

### What it does

This workflow is triggered by every `push` event but has `if: startsWith(github.ref, 'refs/tags/v')` guards on all three jobs, so it only executes when a version tag (e.g. `v0.11.0`) is pushed. It builds the Python distribution, publishes to PyPI using trusted publishing (OIDC), signs the artifacts with Sigstore, and creates a GitHub Release.

### Jobs

The workflow defines three jobs with explicit dependencies:

```

```

Sources: [.github/workflows/release.yml L6-L80](https://github.com/mwclient/mwclient/blob/47ea5b29/.github/workflows/release.yml#L6-L80)

### Job: build

[.github/workflows/release.yml L6-L27](https://github.com/mwclient/mwclient/blob/47ea5b29/.github/workflows/release.yml#L6-L27)

Runs `python3 -m build` to produce both the source tarball (`.tar.gz`) and binary wheel (`.whl`) via the `hatchling` build backend (configured in `pyproject.toml`). The output is stored as the `python-package-distributions` artifact.

### Job: publish-to-pypi

[.github/workflows/release.yml L28-L48](https://github.com/mwclient/mwclient/blob/47ea5b29/.github/workflows/release.yml#L28-L48)

Downloads the distribution artifact and publishes using `pypa/gh-action-pypi-publish`. This uses **PyPI trusted publishing** (OIDC): no PyPI API token is stored in repository secrets. The job requests `id-token: write` permission, which GitHub Actions uses to generate a short-lived OIDC token that PyPI verifies. The deployment environment is named `pypi`.

### Job: github-release

[.github/workflows/release.yml L49-L81](https://github.com/mwclient/mwclient/blob/47ea5b29/.github/workflows/release.yml#L49-L81)

1. Downloads the built distributions.
2. Signs all `.tar.gz` and `.whl` files using `sigstore/gh-action-sigstore-python`, which produces `.sigstore` certificate and signature bundles alongside each artifact.
3. Creates a GitHub Release named after the tag (`github.ref_name`) using the `gh` CLI.
4. Uploads all files from `dist/` (packages + Sigstore signatures) to the GitHub Release.

Requires `contents: write` permission to create releases and `id-token: write` for Sigstore signing.

## Dependabot Configuration

[.github/dependabot.yml L1-L8](https://github.com/mwclient/mwclient/blob/47ea5b29/.github/dependabot.yml#L1-L8)

Dependabot is configured to check the `github-actions` package ecosystem daily and open pull requests when new versions of any pinned Actions are available. This keeps pinned SHA hashes (used in `tox.yml`, `integration.yml`, and `release.yml`) up to date automatically.

```

```

All three workflow files pin Actions to specific SHAs (e.g. `actions/checkout@v6`, `coverallsapp/github-action@5cbfd81b...`, `pypa/gh-action-pypi-publish@ed0c53931b...`) rather than mutable tags. Dependabot raises PRs when upstream releases move.

This page covers how mwclient implements lazy, paginated iteration over MediaWiki API query results. It explains the class hierarchy in `mwclient/listing.py`, how continuation tokens drive chunk loading, how chunk size and result count are controlled, and how raw API dicts are dispatched into typed page objects.

For information on the individual listing methods exposed on `Site` (e.g. `allpages`, `search`, `recentchanges`), see [Site-Level Listing and Query Methods](/mwclient/mwclient/2.5-site-level-listing-and-query-methods). For information on listing methods on `Page` objects (e.g. `backlinks`, `categories`, `revisions`), see [Page Listings and Navigation](/mwclient/mwclient/3.3-page-listings-and-navigation).

## The List Base Class

`List` is the engine behind all lazy iteration. It holds state for a single paginated query and drives chunk loading on demand.

### Construction Parameters

| Parameter | Type | Description |
| --- | --- | --- |
| `site` | `Site` | The site to query |
| `list_name` | `str` | MediaWiki list name (e.g. `'allpages'`) |
| `prefix` | `str` | Two-letter API parameter prefix (e.g. `'ap'`) |
| `api_chunk_size` | `int \| None` | Items requested per API call |
| `max_items` | `int \| None` | Total items to yield before stopping |
| `return_values` | `str \| tuple \| None` | Field(s) to extract from each raw dict |
| `limit` | `int \| None` | **Deprecated.** Alias for `api_chunk_size` |

When constructed, `List` calls `handle_limit` (from `mwclient/util.py`) to resolve the deprecated `limit` parameter and normalize `api_chunk_size` and `max_items`. If `max_items` is set but `api_chunk_size` is not, the chunk size is automatically set to `min(max_items, site.api_limit)` to avoid fetching unnecessary items.

Sources: [mwclient/listing.py L11-L64](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/listing.py#L11-L64)

Key behaviors:

* `self._iter` is a standard Python iterator over the current page's results. It is exhausted one item at a time.
* When `_iter` is exhausted, `load_chunk()` is called to fetch the next page.
* `self.last` is set to `True` when the API response contains no `continue` key, preventing further fetches.
* Timestamps in items are automatically converted via `parse_timestamp` before being yielded.

## Continuation Tokens and Miser Mode

### New-Style Continuation

Since MediaWiki 1.26, the API returns a top-level `continue` dict with opaque continuation values. `load_chunk` merges these directly into `self.args`:

```sql
data['continue'] == {'apcontinue': 'Kre_Mbaye', 'continue': '-||'}
→ self.args.update({'apcontinue': 'Kre_Mbaye', 'continue': '-||'})
```

On the next `load_chunk` call, the updated `args` are passed to `site.get`, fetching the next page of results.

Sources: [mwclient/listing.py L98-L129](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/listing.py#L98-L129)

### Miser Mode

MediaWiki wikis with miser mode enabled may return an API response that contains a `continue` token but zero result items. Without special handling this would cause the iteration loop to spin on an empty `_iter` forever.

The `__next__` loop handles this explicitly: it keeps calling `load_chunk()` on empty `_iter` exhaustion until it either finds a non-`None` item or `self.last` becomes `True`. See [mwclient/listing.py L73-L84](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/listing.py#L73-L84)

 and the referenced GitHub issue in the comments.

Sources: [mwclient/listing.py L73-L84](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/listing.py#L73-L84)

## set_iter: Handling Different Response Shapes

The `set_iter` method maps the API response `data` dict to `self._iter`. The base `List` implementation handles two shapes:

| Shape | Condition | Action |
| --- | --- | --- |
| `result_member` absent | `result_member not in data['query']` | `_iter = iter(range(0))` (empty) |
| List | `data['query'][result_member]` is a `list` | `_iter = iter(list)` |
| Dict | otherwise | `_iter = iter(dict.values())` |

`NestedList` overrides `set_iter` to descend one level: `data['query'][result_member][nested_param]`. This is used for API responses like `checkuserlog` where entries are nested under an extra key.

`PageProperty` overrides `set_iter` to locate the queried page by title inside `data['query']['pages']` and iterate over its property list (e.g. `revisions`, `categories`).

When acting as a MediaWiki generator (not a list), `GeneratorList` also:

* Renames the limit parameter from `{prefix}limit` to `g{prefix}limit` (e.g. `aplimit` → `gaplimit`)

## PageProperty and RevisionsIterator

`PageProperty` is used for per-page API property queries (e.g. `revisions`, `extlinks`). Unlike `List`, it is bound to a specific `Page` object and sets `self.generator = 'prop'`.

Its `set_iter` loops through `data['query']['pages']` to find the page matching `self.page.name` by title, then iterates over `page.get(self.list_name, ())`. If the page is not found in the response (e.g. the API returned a different page), `StopIteration` is raised immediately.

`RevisionsIterator` overrides only `load_chunk` to resolve a conflict between `rvstartid` and `rvstart`: if both are present, `rvstart` is dropped on the first actual fetch. This allows callers to supply both and have the more specific `rvstartid` take precedence after the first API call.

Sources: [mwclient/listing.py L355-L403](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/listing.py#L355-L403)

## api_chunk_size vs max_items

These two parameters serve distinct purposes and are frequently confused.

| Parameter | Scope | Effect |
| --- | --- | --- |
| `api_chunk_size` | Per API request | Sets `{prefix}limit` in the request; controls how many items the server returns per round-trip |
| `max_items` | Total iteration | Stops yielding after this many items, regardless of how many were fetched |

**Example behavior with both set:**

* `max_items=2, api_chunk_size=1`: Two API calls are made, one item yielded per call. Total items yielded: 2.
* `max_items=2` (no chunk size): Chunk size is auto-set to `min(2, site.api_limit)`, so a single API call returns both items at once.
* `api_chunk_size=2` (no max_items): All items are yielded, two fetched per call.

The deprecated `limit` parameter is equivalent to `api_chunk_size` but is preserved for backward compatibility. It generates a `DeprecationWarning` if used.

## return_values: Extracting Fields from Raw Dicts

By default, `List.__next__()` yields raw `dict` objects. The `return_values` constructor parameter changes this:

| `return_values` value | Yield type | Example |
| --- | --- | --- |
| `None` (default) | `dict` | `{'pageid': 1, 'ns': 0, 'title': 'Foo'}` |
| `'title'` (string) | scalar | `'Foo'` |
| `('title', 'ns')` (tuple) | `tuple` | `('Foo', 0)` |

This extraction happens at the end of `List.__next__()` and is skipped if the instance is a `GeneratorList` (since `GeneratorList` has its own `__next__` that converts dicts to page objects).

Sources: [mwclient/listing.py L90-L96](https://github.com/mwclient/mwclient/blob/47ea5b29/mwclient/listing.py#L90-L96)

## Static Helper Methods

`List` exposes three static methods used when constructing listing instances from higher-level code:

| Method | Signature | Purpose |
| --- | --- | --- |
| `generate_kwargs` | `(prefix, **kwargs)` | Yields `(prefixed_key, value)` pairs, filtering out `None` and `False` values |
| `get_prefix` | `(prefix, generator=False)` | Returns `'g' + prefix` if `generator=True`, else `prefix` |
| `get_list` | `(generator=False)` | Returns `GeneratorList` class if `generator=True`, else `List` class |

These are used in methods like `Category.members()` to build the correct class and parameters depending on whether the caller wants a generator (yielding page objects) or a plain list (yielding dicts).

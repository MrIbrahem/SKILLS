This page documents the end-to-end workflow a maintainer follows to cut a new mwclient release: bumping the version, creating the tag, and the automated pipeline that builds, signs, and publishes the package. For information about the CI test workflows that run on every push and pull request, see [7.2](/mwclient/mwclient/7.2-cicd-workflows).

---

## Overview

The release process has two phases:

1. **Manual phase** — the maintainer updates the changelog, runs `bump-my-version`, and pushes an annotated tag.
2. **Automated phase** — pushing a tag matching `refs/tags/v*` triggers `.github/workflows/release.yml`, which builds the distribution, publishes it to PyPI, signs the artifacts with Sigstore, and creates a GitHub Release.

## Version Management

### Version source of truth

The version string is stored in exactly one place: the `__version__` variable in `mwclient/client.py`. The `pyproject.toml` instructs hatchling to read from that location at build time.

| Configuration key | Value |
| --- | --- |
| `[tool.hatch.version]` path | `mwclient/client.py` |
| Pattern searched | `__version__ = '{current_version}'` |
| Replaced with | `__version__ = '{new_version}'` |

## Build System

The package uses `hatchling` as its PEP 517 build backend, configured in `pyproject.toml`.

```
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

The `build` job in `release.yml` installs `pypa/build` and runs `python3 -m build`, which produces both a source tarball (`.tar.gz`) and a binary wheel (`.whl`) in the `dist/` directory.

Files excluded from the source distribution (`sdist`):

| Excluded path | Reason |
| --- | --- |
| `/.flake8` | Linting config, not needed by users |
| `/.gitattributes` | Git metadata |
| `/.github` | CI workflows |
| `/.readthedocs.yaml` | Docs build config |

### Job: build

[.github/workflows/release.yml L6-L26](https://github.com/mwclient/mwclient/blob/47ea5b29/.github/workflows/release.yml#L6-L26)

1. Checks out the repository at the tagged commit (`fetch-depth: 0`).
2. Sets up Python 3.x.
3. Installs `pypa/build` via pip.
4. Runs `python3 -m build`, producing `dist/*.tar.gz` and `dist/*.whl`.
5. Uploads the `dist/` directory as the `python-package-distributions` artifact for downstream jobs.

### Job: publish-to-pypi

[.github/workflows/release.yml L28-L47](https://github.com/mwclient/mwclient/blob/47ea5b29/.github/workflows/release.yml#L28-L47)

* Downloads the `python-package-distributions` artifact.
* Publishes using `pypa/gh-action-pypi-publish@ed0c53931b1dc9bd32cbe73a98c7f6766f8a527e`.
* No API token is used. Authentication relies on **OIDC trusted publishing**: the job is granted `id-token: write` permission, and the GitHub Actions OIDC provider issues a short-lived token that PyPI verifies against a pre-configured trusted publisher entry for the `pypi` GitHub Actions environment.

### Job: github-release

[.github/workflows/release.yml L49-L80](https://github.com/mwclient/mwclient/blob/47ea5b29/.github/workflows/release.yml#L49-L80)

This job runs after `publish-to-pypi` succeeds. It:

1. Downloads the distribution artifacts from the `python-package-distributions` artifact.
2. Signs all `.tar.gz` and `.whl` files using `sigstore/gh-action-sigstore-python`. This produces `.sigstore.json` bundle files alongside the distributions in `dist/`.
3. Creates a GitHub Release for the tag using `gh release create '${{ github.ref_name }}'` with empty release notes (notes can be filled in manually after).
4. Uploads all files from `dist/` — including distribution files and Sigstore signature bundles — to the GitHub Release using `gh release upload`.

## Artifact Signing with Sigstore

Sigstore's `gh-action-sigstore-python` signs the distribution files using the GitHub Actions OIDC identity. The inputs passed to the action are:

```
./dist/*.tar.gz ./dist/*.whl
```

The result is a set of `.sigstore.json` bundle files in `dist/` that consumers can use to verify the provenance of the release artifacts without needing a traditional GPG key.

Sources: [.github/workflows/release.yml L66-L69](https://github.com/mwclient/mwclient/blob/47ea5b29/.github/workflows/release.yml#L66-L69)

## Pre-release Checklist

| Step | Detail |
| --- | --- |
| Update `CHANGELOG.md` | Summarize changes since the last release |
| Run `bump-my-version bump major\|minor\|patch` | Updates `mwclient/client.py` and `README.md`, commits, and tags |
| Verify the commit | Check that `__version__` in `client.py` is correct |
| `git push && git push --tags` | Pushes the commit and the `vX.Y.Z` tag; triggers `release.yml` |
| Monitor the Actions run | Confirm all three jobs (`build`, `publish-to-pypi`, `github-release`) succeed |
| Edit GitHub Release notes | Add a human-readable summary if desired (the action creates the release with empty notes) |
